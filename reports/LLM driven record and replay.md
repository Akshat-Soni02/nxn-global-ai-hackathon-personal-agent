# Feed Nemotron evidence, keep replay deterministic

Task Player should keep its hybrid design, where **code records facts and writes locators, the model adds meaning, and code checks the model against the recording**. What should change is that the model gets far more evidence (the user's stated goal before Record, hover, the page or accessibility context around each target, and cropped before/after frames for the steps text cannot explain), and that replay gains LLM rescue rungs so a missed step is healed instead of stopping the run. OpenAI's Record & Replay takes the other route. A native helper captures macOS accessibility events with no model running, one LLM turn after "done" writes a plain-language SKILL.md, and a fresh agent re-perceives the screen on every run. That makes it adaptive, but it pays for a model loop on every run, and the best live web agents finish only **56–61% of tasks** ([Online-Mind2Web](https://arxiv.org/html/2504.01382)), which is too unreliable for a chore that repeats weekly. The skills that failed this week look like the **code-only path**, with no `.env` key and template intents, so the first move is to turn the model on, recompile those traces, and run the ten baseline tests in section 6 before changing the architecture. On Nebius there are **two $25 Token Factory grants** (the hackathon form and the Builders Program), the deadline is **30 October 2026 at 10:00 PT** with judging through 15 December, and Token Factory issues only bearer API keys, so a small proxy must hold the key. **No NVIDIA model on Token Factory can read an image today**, so Nemotron 3.5 Lightning, 3 Super and 3 Ultra should do all the reasoning while a non-NVIDIA vision model turns pixels into text for them. The skill-id collision is already fixed: every recording now gets its own id.

## OpenAI calls the model before and after recording, never during

**This section answers: how does OpenAI's Record & Replay work end to end, and where do comparable products put their LLM calls?** OpenAI ships the feature as a bundled plugin with two halves. One is an `event-stream` MCP server, launched by the Computer Use helper as `SkyComputerUseClient event-stream mcp`, which exposes `event_stream_start`, `event_stream_status` and `event_stream_stop` ([openai/codex #29051](https://github.com/openai/codex/issues/29051)). The other is a `record-and-replay` skill that tells the model what to do with the recording ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)). The user opens Plugins, picks **Record a skill** from the + menu, and reviews a suggested prompt before submitting it. OpenAI's main tip is the intent prompt: **"State your goal and any specific inputs that might vary between skill uses before you start recording"** ([ChatGPT Learn](https://learn.chatgpt.com/docs/extend/record-and-replay)). A real start prompt reads "Record me entering work hours in the attendance app so I can repeat the same actions in the future" ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)).

That first model turn calls `event_stream_start`, which shows a permission prompt, and then stops on purpose. The bundled skill says: "After `event_stream_start` succeeds, **do not sleep, poll, or wait in a loop** for the user to finish. End your turn" ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)). No model runs while the user demonstrates.

During the demo the native helper captures what OpenAI calls "the actions and window content needed to learn the workflow" ([ChatGPT Learn](https://learn.chatgpt.com/docs/extend/record-and-replay)). A hands-on write-up says that covers apps and windows, mouse and keyboard actions with their target elements, focused elements, selected text, and **the accessibility tree and its changes**. It is written to `session.json` (timing, end reason) and `events.jsonl` (the events). The one published event line shows a click carrying `app.name`, `window.title`, `window.url` and an AX target with `role`, `subrole` and `description` ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)). Two design choices stand out. Typing is stored as the field's **final value** rather than as keystrokes. AX changes are stored as compact diffs that mark elements as changed, added or removed, so a menu that appeared after a hover shows up as an added element even though no hover event is logged.

Recording needs Accessibility and Screen Recording permission because it is "built on top of the Computer Use machinery". **No published source shows screenshots inside the recording**, so whether OpenAI keeps any pixels is unconfirmed. Two often-repeated claims are weaker than they look. The **30-minute cap** comes from a third-party paraphrase of the tool description ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)). The claim that OpenAI captures "spoken user context" comes from a Linux reimplementation, while OpenAI's own docs say only "actions and window content" ([distsystem/codex-desktop-linux](https://github.com/distsystem/codex-desktop-linux/blob/main/docs/record-and-replay-linux.md)).

The user ends the recording from the menu bar, from the overlay, or by telling the chat they are done. A second model turn calls `event_stream_stop` and reads both files from disk. It is told to "Treat `events.jsonl` as the primary evidence" and to pay special attention to selection events, selected text, focused elements and targets. If the evidence is thin, the rule is **"do not guess. Explain what is unclear and ask the user"**. The turn then follows the `skill-creator` workflow, including validation. Its most important instruction is to **"treat the recording as evidence of the user's intended outcome, not a requirement to reproduce every UI action"**. It should prefer a connector when one exists, name stable app, window and control targets, include verification steps, avoid coordinate-only replay, and replace sensitive values with placeholders ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/); corroborated by [dev.to](https://dev.to/ahab_indieseek/codex-record-replay-principles-3j6d)).

The SKILL.md it writes is ordinary natural language and must have a `name` and a `description` ([Build skills](https://learn.chatgpt.com/docs/build-skills)). In the published example, `enter-timeport-work-hours`, the description carries trigger wording ("Use when the user asks to enter, register, repeat, or correct monthly work hours…"). A Collect Inputs section says **"Treat the recorded values as examples, not defaults … Never infer a date, project, description, or duration from the recorded demonstration."** An Open section confirms the page title before editing. The steps are anchored on accessible labels, such as "the control whose accessible description identifies that date's work-effort entry". A Verify section checks outcomes ("confirm the visible daily or monthly total changed consistently") and says to stop rather than retry a save, to avoid duplicate entries. A Safety section closes it ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)). Skills load by progressive disclosure. The model first sees only each skill's name and description, which together use at most 2% of context or 8,000 characters, and opens the full file only when it picks that skill ([Build skills](https://learn.chatgpt.com/docs/build-skills)).

Replay has no script. The user starts a new chat, mentions the skill (`@` in ChatGPT, `$` in Codex), and gives "the values that are different this time". The product uses the skill "as reusable context" and does the work with Computer Use, browser actions or plugins ([ChatGPT Learn](https://learn.chatgpt.com/docs/extend/record-and-replay)). Computer Use's `get_app_state` returns a screenshot and an accessibility tree, so every replay re-perceives the screen ([openai/codex #29051](https://github.com/openai/codex/issues/29051)). OpenAI documents **no separate heal step and no deterministic fast path**, so every run is an LLM loop.

The comparable products fall into three designs, which differ in when the model runs and what the artefact is.

| Product (status) | LLM before or during recording | LLM after recording | Artefact | Replay and healing |
|---|---|---|---|---|
| OpenAI Record & Replay (macOS, June 2026) | One turn to start, then none | Reads events, writes the skill via skill-creator ([ChatGPT Learn](https://learn.chatgpt.com/docs/extend/record-and-replay)) | Natural-language SKILL.md | Agent on every run; no heal step documented |
| browser-use workflow-use ("very early development") | Optional goal string; none during | Turns events (plus optional screenshots, **off by default, max 20**) into workflow JSON with an `input_schema` ([service.py](https://github.com/browser-use/workflow-use/blob/main/workflows/workflow_use/builder/service.py)) | Deterministic steps with selectors, plus `agent` steps for dynamic lists and calendars ([prompts.py](https://github.com/browser-use/workflow-use/blob/main/workflows/workflow_use/builder/prompts.py)) | Code first; per-step agent fallback its own README calls "currently really bad" ([README](https://github.com/browser-use/workflow-use)) |
| Skyvern code caching | The first agent run is the model | Code generated from that run's actions | Cached code per block | "No screenshots, no LLM reasoning"; on failure it falls back to the agent and **regenerates the cache** ([Skyvern](https://www.skyvern.com/docs/developers/features/code-caching)) |
| UiPath Healing Agent + ScreenPlay | not found | Coding agents generate deterministic RPA | RPA with a few natural-language ScreenPlay steps | "Maximally deterministic, minimally agentic" ([ScreenPlay](https://docs.uipath.com/agents/automation-cloud/latest/user-guide-screenplay/best-practices)); runtime heals of selectors, delays and pop-ups ([Healing Agent](https://docs.uipath.com/agents/automation-cloud/latest/user-guide-ha/what-is-healing-agent)) |
| Power Automate Record with Copilot (**deprecated**, Aug 2026) | Captured voice narration, mouse and keyboard | Analysed "your actions and narration" after Done ([MS Learn](https://learn.microsoft.com/en-us/training/modules/build-microsoft-power-automate-flow/9-build-basic-desktop-flow-use-record-copilot)) | Editable desktop flow | Desktop flow ([deprecation](https://learn.microsoft.com/en-us/power-automate/desktop-flows/create-flow-using-ai-recorder)) |
| Claude in Chrome workflow recording | not documented | not documented | A saved, schedulable "shortcut" ([Anthropic](https://support.claude.com/en/articles/12012173-get-started-with-claude-in-chrome)) | Claude agent; detail not documented |
| Google Mariner "teach and repeat" (shut down May 2026 per press) | not documented | not documented | "Learns plans" ([Google](https://blog.google/technology/ai/io-2025-keynote/)) | Screenshot-driven agent ([TechSpot](https://www.techspot.com/news/112334-project-mariner-dead-but-google-browser-controlling-ai.html)) |

Three patterns hold across the table. **Every product that documents a compile step takes intent as an input**: OpenAI's typed prompt, Power Automate's narration, workflow-use's `{goal}` slot. **Every product that documents variable detection does it with the LLM at compile time.** **None sends a screenshot for every event by default.**

The products split at replay. OpenAI pays for an agent on every run, while Skyvern, workflow-use and UiPath run code and call a model only when a step fails or when the content is dynamic by nature. The research favours the second design for a weekly chore. On live websites, Operator completes 61.3% of tasks, Claude Computer Use 3.7 56.3%, and SeeAct and Browser Use about 30% ([Online-Mind2Web](https://arxiv.org/html/2504.01382)). On OSWorld, humans scored 72.36% against 12.24% for the best model of its time ([OSWorld](https://arxiv.org/abs/2404.07972)).

The strongest case for OpenAI's design is that natural-language skills absorb UI change without heal machinery, and people can read them. Task Player can keep both benefits by borrowing OpenAI's natural-language header (description, inputs as examples, outcome verification) while keeping deterministic JSON steps underneath. No published study compares deterministic and agentic replay on the same tasks over time, so this conclusion rests on indirect evidence and on cost: a clean deterministic run makes zero model calls.

## Code writes the facts, the model writes the meaning

**This section answers: should the skill file be built by code plus AI or by AI alone, and how deep should normalisation go so each action's meaning is worked out at compile time?** Today's pipeline already divides the work, and the division is sound. Code builds a skeleton that fixes each step's channel, action, target and recorded values. Its header says the model "can only add meaning on top: it can never invent a selector or an action" ([skeleton.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/skeleton.ts)). The model may return only `Annotations`: intents, inputs, triggers, success checks, per-step checks, waits and approvals, plus a capped list of questions. "Targets, channels and actions are deliberately absent." Code then checks the merged result against the same zod `Skill` schema and the template checks, sends errors back for up to three attempts, and saves the skeleton if the model never passes ([compile.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/compile.ts)).

That fallback is why a skill exists even with no model, and it is also why this week's skills read like templates. With no key, compile logs "No model configured (NEBIUS_* in .env), so the skill was built by code only", and the intents become `Click ${what}`. The saved skills match that path. The Google skill keeps "Click 'Seek slider'" twice. The YouTube skill hard-codes a `watch?v=…&list=RD…` address. The Maps step s3 has no role, only text, `near` and fallbacks. As of 7 October the repo has a `.env.example` and no `.env` ([.env.example](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/.env.example)). That suggests, but does not prove, that no key was set when these were recorded. Part of "the skills are not logically built" is therefore **the code running without its model**. The cheapest experiment is to set the key and rerun `compile <session>` on the same traces before redesigning anything.

Even with the key set, the model is nearly blind. `forModel` gives it about ten text fields per step (kind, URL, role, name, label, `near`, value, `led_to`, `produced` and similar), but **no screenshot, no goal sentence, no hover, no siblings or list position, and nothing about what was on screen before the click** ([compile.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/compile.ts)). With that input it cannot tell "the first search result" from "this exact video", or a deliberate click from an incidental one. This week's five failures sort by layer:

| Failure | Root cause | Fix and where it lives |
|---|---|---|
| YouTube "Play" shown only on hover, recorded as a bare click | Capture gap: no hover events, and no hover action in the schema ([skill.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/core/src/skill.ts)) | Code: track pointer dwell, check whether the target was visible beforehand, attach a `revealed_by` hover precondition. A model cannot recover a hover nobody recorded |
| Maps URL check copied `@lat,lng,zoom` | Normalise rule | Code: `pagePath` with `CHANGES_EACH_VISIT` (uncommitted edit in [skeleton.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/skeleton.ts)) |
| Click on a feed item that changes on every visit | Ambiguous intent and no selection rule | Model: ask "this video, or the first result for your search?", then a `select: first` rule within the results container. Code's `linkDestination` turns the click into a navigate, which is right only for "this exact item" |
| Recording began on another extension's new-tab page | A page replay can't open | Code: `opensOnReplay` already drops it ([normalise.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/normalise.ts)) |
| Intents like "Click 'Play'" | Code-only compile and a blind model | Model: turn it on and give it the goal and captions. This is its core job |

**An AI-only skill would be worse.** Its output would vary from compile to compile, its selectors and actions could not be traced to the recording, its prompts would carry full DOMs or frames, nothing would guarantee it parses for the player, and every replay's success would be capped by agent grounding, the weakest link in the research. The evidence favours demonstrations plus induced structure, not replacing the demonstration. Induced workflows raised relative success by **24.6% on Mind2Web and 51.1% on WebArena** ([Agent Workflow Memory](https://arxiv.org/abs/2409.07429)). Models understood workflows from demonstrations **93%** of the time but completed only **40%** end to end from a description alone ([ECLAIR](https://arxiv.org/abs/2405.03710)).

**Normalisation should go deep in two different layers.** The mechanical layer stays code, because its own header says "Mechanical rules only, so the compiler's input is stable and testable" ([normalise.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/normalise.ts)). It merges keystrokes, removes focus clicks, drops pages replay can't open, cuts per-visit URL segments and turns link clicks into navigates. Two additions belong in this layer: attaching `revealed_by` when a hover exposed the target, and flagging suspected noise, such as the seek-slider clicks, instead of deleting it. The meaning layer moves into compile and works on every action, through new optional fields proposed in the research notes (they are not shipped code):

| Field | Level | What it holds |
|---|---|---|
| `why` | Step | What the step achieves, not how |
| `target_description` | Step | Plain-language description of the target, for the replay model |
| `select` | Step | `exact`, `first`, `nth`, `newest` or `by_text`, within a container locator |
| `precondition` | Step | A hover, or another state that must hold first |
| `expect` | Step | Plain-language postcondition for a judge |
| `stable` | Step | False for feed and preview elements |
| `goal`, `done_when` | Skill | The user's own words, and the finish condition |

Every model claim should cite step ids and evidence, and code should lint those claims against the recording itself. A URL check may not contain per-visit segments. Every "text visible" check must actually hold in the recorded after-state. A target that wasn't visible before the click must carry a hover precondition. A step flagged as noise is dropped only after the user confirms it in the drill. A read-only SKILL.md rendered from the JSON gives people and the replay model OpenAI's readable view, while JSON stays the source of truth the player parses. A clean run still reads only JSON and makes **zero model calls**, because the new fields are read only by the dry run and by rescue. These schema additions need sign-off from both the record and replay owners, as `skill.ts` requires ([skill.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/core/src/skill.ts)).

Separately, the id-collision bug is **fixed in the working tree**. `newSkillId` gives every recording a readable name plus a random six-character tag, such as `upload-invoice-k3f9q2`, and `findSkills` lets `run upload-invoice` find that full id when the prefix is unique ([skill-store.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/apps/daemon/src/skill-store.ts)).

## Capture a frame at every event, send only the ambiguous ones

**This section answers: should Task Player take a screenshot at each captured event, in the browser and on the Mac, and send screenshots plus events to an LLM at compile time?** Capture them locally, yes. Send all of them, no.

**In Chrome**, `chrome.tabs.captureVisibleTab` works with the `<all_urls>` permission the extension already declares and shows no debugger bar. It is capped at **2 calls per second**, `MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND` ([Chrome tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)), and real extensions hit that quota ([UI.Vision forum](https://forum.ui.vision/t/error-this-requeste-exceeds-the-max-capture-visible-tab-calls-per-second-quota/8024)). A true "before click" frame is racy, because the call hops through the service worker and some UIs act on pointer-down. The workable recipe takes the pre-frame when the pointer has rested about 300 ms on an interactive element, which also captures the hover state YouTube's Play button needed. It takes the post-frame once the page settles, skips frames for typing, drops low-priority frames rather than blocking when over quota, and crops in the service worker using the element rect times `devicePixelRatio`. Chrome's own DevTools Recorder skips hover because it "pollutes the recording" ([DevTools Recorder](https://developer.chrome.com/docs/devtools/recorder/reference)), so log only hovers that dwell and that revealed the later target. During replay, CDP `Page.captureScreenshot` with a `clip` is better, since the debugger is already attached ([Page.pdl](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Page.pdl)).

**On the Mac**, `CGWindowListCreateImage` has been deprecated since Sonoma. Its replacement, `SCScreenshotManager` with a single-window `SCContentFilter`, needs macOS 14 or later and the Screen Recording permission ([Apple docs](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager); [Apple forums](https://developer.apple.com/forums/thread/740493)). Sequoia re-asks for that permission monthly ([9to5Mac](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/)), so make it optional and degrade the way the app already does when Accessibility is missing. The global event monitor sees events only after they happen, so treat Mac frames as after-frames.

**Redact before anything touches disk.** Black out password fields, `cc-*` and one-time-code autocomplete fields, and AX secure text fields. Then send crops and a downscaled context frame, never raw frames. That honours the design rule that data leaves the Mac "only when compiling a skill or recovering a failed step" and that snapshots "are cut to the area around the target" ([design.md](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/docs/design.md)). A masked DOM snapshot in the style of rrweb is a cheaper, more redactable text complement to pixels ([rrweb](https://github.com/rrweb-io/rrweb/blob/master/guide.md)). The `ElementDescriptor.crop` slot already exists, but nothing fills it ([descriptor.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/core/src/descriptor.ts)).

The selective-send rule follows from the grounding research. On OSWorld, **text-only GPT-4 on the accessibility tree scored 12.24%**, the same as GPT-4V with screenshot plus tree (12.17%), while screenshot alone scored **5.26%** ([OSWorld](https://arxiv.org/html/2404.07972)). SeeAct found the best grounding "leverages both the HTML structure and visuals" ([SeeAct](https://arxiv.org/abs/2401.01614)). WILBUR's text-only agent came within 5% of a multimodal one ([WILBUR](https://arxiv.org/abs/2404.05902)). Pixels help most where text is thin: canvas-drawn apps such as Sheets, Maps and Figma, icon-only controls, hover-revealed targets, and items picked from a list. Compile should therefore run in two stages. Stage A makes one vision call per ambiguous step, showing the before and after crops side by side with the DOM or accessibility context, and returns a structured caption: what changed, what the element is, whether it appeared on hover, and whether it varies per visit. Stage B is one text call over the goal, the captions, today's text fields, the skeleton and memory. Navigations, file moves and AX menu paths skip Stage A entirely.

**Here the notes conflict, and the newer, primary-sourced finding wins.** The pipeline note designed Stage A around Nemotron Nano 12B v2 VL (up to 4 images per request) and Nemotron 3 Nano Omni (1 image per prompt in its serving example), using limits taken from their Hugging Face model cards ([Nano VL card](https://huggingface.co/nvidia/NVIDIA-Nemotron-Nano-12B-v2-VL-BF16); [Omni card](https://huggingface.co/nvidia/Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16)). The Nebius note checked the live Token Factory catalogue on 7 October 2026 and the August deprecation notice. It found that **Omni was removed from serverless on 31 August 2026**, replaced by the text-only Nemotron 3.5 Lightning ([August 2026 deprecations](https://docs.tokenfactory.nebius.com/august-2026-deprecation-notice)), and that **Nano 12B v2 VL was never in the serverless catalogue** ([catalogue](https://tokenfactory.nebius.com/api/public/models_info)). Stage A therefore runs on a non-NVIDIA vision model on Token Factory, **GLM-5.3-Flash** or **Qwen3.8-27B**, and its captions become text that Nemotron compiles. Stitching before and after into one image still halves the number of calls, but no model limit forces it any more.

Image size drives the cost. Qwen3.8-27B spends about one visual token per 32×32 pixels, which is roughly **1,000 tokens at 1280×800 versus about 5,040 at Retina 2880×1800** ([Qwen3.8 preprocessor](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/preprocessor_config.json)), so downscale to about 1280 px wide. At catalogue prices, ten keyframes per compile cost about **$0.008 on Qwen3.8 and about $0.002 on GLM-5.3-Flash**. Both figures are computed from assumed token counts, and GLM's image-token count is unverified ([catalogue](https://tokenfactory.nebius.com/api/public/models_info)). Two things remain untested: whether JSON-schema output works together with image input on these endpoints, and how much disk a frame really takes.

## Live model calls earn a place in three recording moments

**This section answers: in which scenarios is an LLM needed during recording, given that today it sees only the finished trace and misses context?** Almost everything the after-Stop model misses is **evidence that was never captured**, not reasoning that had to happen live. Most of the fix is therefore better capture, done in code. OpenAI itself runs no model during the demo ([azukiazusa.dev](https://azukiazusa.dev/en/blog/workflow-to-reusable-skill/)).

| What the compile model misses | Example from this week | Captured by | Live LLM needed? |
|---|---|---|---|
| The goal and what counts as success | "play music": any song, or this one? | Goal text box before Record | No; optional clarifying questions |
| What was on screen before the action, including hover | YouTube Play visible only on hover | Dwell ring buffer, pre-frame | No |
| Alternatives on screen | Feed card 1 of 20; "Rameshwaram Cafe" suggestion | DOM or AX context at event time | No |
| What the user read but didn't click | Checked a price, then bought | Post-frame or masked DOM snapshot | No |
| Why one item was chosen | "the cheapest", "today's row" | Ask at the moment | Optional |
| False starts | Seek-slider clicks | Keep them with a noise flag | No |
| Canvas targets | A click on a map | Frame plus click point as evidence | Optional vision caption |

Three moments justify a live call. The first is **before Record**. A goal text box mirrors what OpenAI, Power Automate and workflow-use all collect ([workflow-use prompts.py](https://github.com/browser-use/workflow-use/blob/main/workflows/workflow_use/builder/prompts.py)), and one cheap Nemotron call can turn "play music" into one or two pointed questions such as "always this song, or the first result for what you type?". It needs no screen data, so it does not conflict with the privacy rule. The second is **the moment of an ambiguous choice**. When code detects a click on one of three or more same-role siblings, it asks the user right then why that one, and a template phrases the question well enough. The third is **canvas-drawn apps**, where a frame alone may be too ambiguous to read after the fact, so one vision caption per click while the state is still on screen helps. Live calls are not worth it for variable detection, because compile already has the values. Nor for recognising gestures such as hover or drag, which code does deterministically from DOM events. Nor for spotting secrets, where deterministic rules on input types and AX secure fields must run before anything is stored anyway.

Voice narration depends on the vision conflict. Power Automate's recorder captured narration alongside actions ([MS Learn](https://learn.microsoft.com/en-us/training/modules/build-microsoft-power-automate-flow/9-build-basic-desktop-flow-use-record-copilot)), and the pipeline note proposed transcribing a local voice note with Omni after Stop. Omni has left Token Factory and **the current catalogue lists no audio-capable model**, so voice has no Nebius path today and should be deferred.

Every live call has a price. It adds per-event latency and can reorder events unless it runs asynchronously, and its cost scales with events rather than recordings. It also sends data off the Mac while the user works, which contradicts the design rule ([design.md](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/docs/design.md)). If the canvas option is adopted, gate it per site and per recording, send only redacted crops, and update design.md first. No study was found that measures compile quality with versus without a stated goal, so the size of the goal prompt's benefit is a hypothesis for the tests in section 6.

## Replay climbs a five-rung ladder before it asks

**This section answers: how should an LLM at replay handle renamed, moved, removed or changed elements, stale files and links, and a changed Google Sheet?** Today the matcher scores Chrome AX role plus name (0.45), attributes (0.25) and fallback selectors (0.30). It accepts a match at 0.5 or above with a 0.15 margin, and it does not yet use `near`, `text`, `label`, frames or shadow roots ([match.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/player/src/web/match.ts)). Nothing catches a failure: "agent fallback … goes here; until then every failure escalates" ([run.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/player/src/run.ts)). The design already plans a fallback that "may only return targets and actions for the current step's `intent`" and cannot add steps or leave the skill's domains ([design.md](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/docs/design.md)). The research supports building it cheapest-first, with text before vision:

| Rung | What happens | Model | Fires when |
|---|---|---|---|
| 0. Matcher v1 | Adds `near`, `label`, `text`, frames and shadow roots; follows the `select` rule within its container for unstable items | none | Every step |
| 1. Code heals | Dismisses known overlays, scrolls into view, **hovers the `revealed_by` ancestor and re-matches**, waits longer | none | Match returns `none` |
| 2. Text pick | Nemotron chooses among up to 15 AX candidates (id, role, name, near, text, box), given the step's `intent`, `target_description` and crop caption; returns a choice or "none", a confidence and a reason | Lightning; Super with thinking for hard cases | `ambiguous`, or `none` with candidates |
| 3. Vision pick | Set-of-marks screenshot with numbered boxes drawn from DOM or AX rects; returns a mark id | GLM-5.3-Flash or Qwen3.8-27B | No usable AX node: canvas, Sheets grid, Maps |
| 4. Ask | Shows the frame and the candidates | the user | Risky step, low confidence, failed check, or budget spent |

The model always chooses among candidates that code extracted, never free coordinates, which keeps its answers cheap and checkable. Each kind of change maps onto a rung:

| Change at replay | Behaviour today | Recommended handling |
|---|---|---|
| Element moved | Matching isn't positional, so it already works | Rung 0 |
| Element renamed ("Submit" becomes "Send") | Score falls, the run escalates | Rung 2: role, `near` and intent still match. Verify, then learn back |
| Element removed | Escalates | Rung 2 returns none. It may propose **at most one** replacement action inside the skill's domains and verify it, in the style of Playwright's healer, which "suggests a patch" and re-runs ([Playwright](https://playwright.dev/docs/test-agents)). Otherwise ask |
| Element's role or flow changed | Escalates | Stop and ask; never auto-accept a role change |
| Control appears only on hover | Not recorded at all | Capture `revealed_by` while recording; Rung 1 hovers it |
| Stale link | A link click replays as its recorded address ([skeleton.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/skeleton.ts)), so a dead or input-dependent address breaks | *Recommendation:* compile marks links whose destination depends on an input or a feed as re-find steps (`select` plus `target_description`), not navigates. If a navigate lands on an error or fails its check, Rung 2 re-finds the link from the previous page |
| Stale file | The file input picks the newest file "like" the recorded one, with only digits made into wildcards ([normalise.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/recorder/src/normalise.ts)); existence, emptiness and type are checked before step 1 | Files the run itself downloads use `fs.find … since_run_start`, as the hand-written `download-and-file` skill does ([skills/real/README.md](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/skills/real/README.md)). *Recommendation:* a freshness check (modified after the last successful run), asking if it fails. No model needed |
| Sheet column moved | `data.pick` finds columns by header name, ignoring case and spaces ([data-channel.ts](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/packages/player/src/node/data-channel.ts)) | Already fine |
| Sheet header renamed | Fails with "no column X" | Code fuzzy match first, then one Lightning call mapping the old header to the new header list with sample rows. Cache by a hash of the headers; write back after approval |
| Column removed or split | Fails | Ask |
| No row for today | Fails with "no row where Date = …" | Not a heal: the data is genuinely absent, so ask or skip |

Verification follows the same cheapest-first order. The step's machine check (URL, visible text, visible element, file exists) runs first. For healed steps only, an LLM judge then reads the step's `expect` against the after-state. The best published web-task judge, WebJudge, reaches only **about 85% agreement with human judgment** ([Online-Mind2Web](https://arxiv.org/abs/2504.01382)), so a judge must never be the only gate before a step that requires approval.

Learn-back writes version n+1 with the healed locator first and the old one kept as a fallback. It records how the heal happened (rung, model, confidence, before and after crops), and applies automatically only to non-risky steps that have verified on two consecutive runs. This follows the design's own plan and Healenium's "last successful locator" baseline ([Healenium](https://healenium.io/docs/how_healenium_works)). Skyvern does the equivalent at block level by regenerating its cache after a successful agent run ([Skyvern](https://www.skyvern.com/docs/developers/features/code-caching)). Replay should stop and ask when the two best candidates fall within the margin on a risky step, when the chosen element's role differs from the recorded one, when a check fails after a heal, when an action would leave the skill's domains, or when the heal budget is spent. A reasonable budget is two model calls per step, with a per-run cap like the one `data.ai` already has.

### Token Factory is the API; AI Cloud is GPUs you pay for

Token Factory serves open models "via an OpenAI-compatible API", while AI Cloud means "GPU VMs and multi-node clusters" ([Nebius for AI Builders](https://dev.nebius.com/)). Serverless endpoints bill per token with dynamic rate limits. Dedicated endpoints bill per GPU-hour, and custom weights there are "beta and available on request" ([Dedicated endpoints](https://docs.tokenfactory.nebius.com/ai-models-inference/dedicated-endpoints/overview); [Custom weights](https://docs.tokenfactory.nebius.com/ai-models-inference/dedicated-endpoints/custom-weights)). For Task Player, **Token Factory serverless is enough**, since one HTTPS call satisfies the rule. The repo's `.env.example` points `NEBIUS_BASE_URL` at a placeholder, with the comment "our own Nebius Serverless endpoint" and a single `NEMOTRON_MODEL` ([.env.example](/Users/rushil.jariwala/Desktop/nxn-global-ai-hackathon-personal-agent/.env.example)). If "Serverless endpoint" means an AI Cloud Serverless Endpoint, that is GPU-hour billing the credits don't cover. Point it at the global Token Factory URL, `https://api.tokenfactory.nebius.com/v1/` (regional hosts "can stop working" per [Public endpoints](https://docs.tokenfactory.nebius.com/public-serverless)), and split the model setting into small, medium, large and vision variables.

### Hold the key in a proxy, because OAuth does not exist here

The only inference authentication is a bearer API key. The docs warn "do not share or expose them in client-side code. If a key is compromised, Nebius Token Factory can automatically revoke it" ([API auth](https://docs.tokenfactory.nebius.com/api-reference/introduction)), and the SSO in the docs covers console access only ([docs index](https://docs.tokenfactory.nebius.com/llms.txt)). Rate limits are per user and dynamic. A limit rises 20% for the next 15-minute window when use reaches 80% of it, falls by a third below 50%, and tops out at 20× the base. The docs' example baseline is 60 RPM and 400,000 TPM, and over-limit requests get HTTP 429 with `Retry-After` ([Rate limits](https://docs.tokenfactory.nebius.com/ai-models-inference/rate-limits)).

A gitignored `.env`, with a separate "dev" project and key, is right for developer machines only. For the demo and the judges a proxy is required, not just good practice, because the repo must be public, judges must test "free of charge and without any restriction" ([Devpost Rules](https://nebiusglobalaihackathon.devpost.com/rules)), and no per-key spend cap is documented. The proxy carries these controls:

| Control | Why |
|---|---|
| One route per task (`/compile`, `/caption`, `/locate`, `/judge`, `/data-step`), not a raw pass-through | The app never sees the key or the model id |
| Per-install tokens with daily request and token quotas | One judge or one bug can't drain the balance |
| Model allow-list and per-route `max_tokens` | Caps the cost of each call |
| Screenshot downscaling | Retina frames cost about 5× the image tokens |
| Global daily dollar cap from `usage` × catalogue price, with a kill-switch | Protects the auto-charged card |
| Forward `Retry-After`; log rate-limit headers | Clean behaviour under 429s |

End users then never see a token or a bill. "Bring your own Nebius key" can be an advanced setting, not the default.

| Stage B compile (10K tokens in) | No | **Super**, thinking on, JSON schema | Ultra for long recordings or schema failures | ~$0.0075 Super; ~$0.025 Ultra |
| Rung 2 replay pick | No | Lightning | Super with thinking | ~$0.0002; ~$0.002 |
| Rung 3 replay pick (1280 px) | Yes | GLM-5.3-Flash | Qwen3.8-27B; MiniMax-M3 or Kimi only if both fail testing | ~$0.0007; ~$0.0022 (Retina ~$0.0041) |
| Header remap, small `data.ai` | No | Lightning | Super for 20K-token tables | ~$0.0002; ~$0.0065 |
| Classification (skill choice, step type) | No | Lightning, thinking off, ≤10 output tokens | — | ~$0.00003 |

An expensive run, meaning a Super compile with thinking on plus ten Retina-size Qwen3.8 rescues, costs about $0.05, so **$25 covers roughly 500 such runs**. The biggest levers are turning thinking off on fast paths (Nemotron 3.x and Qwen3.8 default to it, and thinking tokens bill as output), downscaling screenshots, and sending candidates as text to get back an id. Thinking is toggled with `chat_template_kwargs: {"enable_thinking": false}` ([Lightning card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16)). Whether Token Factory honours that flag, and whether JSON-schema output works on Nemotron, are both untested, and only MiniCPM carries the "JSON mode" tag ([JSON docs](https://docs.tokenfactory.nebius.com/ai-models-inference/json)). Keep `extractJson` plus zod as the safety net. Keep model ids in one proxy config, because the catalogue removed models in June and August with about a month's notice.

## Conclusion

The question "LLM or code?" turns out to be the wrong axis. Task Player's skills fail because **the model is starved of evidence and was probably switched off**, not because code holds the pen. The goal, the hover, the siblings on screen and the after-state were never captured, so no compile model could infer them, and the highest-value fix sits in the recorder rather than the prompt. A constraint that looks like a handicap reinforces this design. With no NVIDIA vision model on Token Factory, the pipeline must turn pixels into text before Nemotron reasons, which is what the grounding research recommends anyway. It also puts Nemotron at every decision point judges will look for: compile, rescue, data and judging.

OpenAI's real lesson for Task Player is the shape of its meaning layer, not its agent-on-every-run replay: a goal stated up front, inputs treated as examples, verification phrased as outcomes, and "ask, don't guess". Task Player can adopt all of that while keeping deterministic replay that heals and writes back, as Skyvern and UiPath do. The sequence follows directly. Add the key, recompile this week's traces and run the ten baseline tests. Then add the goal prompt, capture hover, frames and context, add the caption pass and lints, finish the matcher, and build text rescue with learn-back before vision rescue. Because every step is measured against the same ten tests, the team will know which change earned its keep.
